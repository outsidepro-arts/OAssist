# OAssist

OAssist - Android-приложение для общения с LLM и работы системного ассистента.
Основная аудитория - незрячие пользователи. Весь UI должен быть доступен с экранным чтецом.

- Пакет: `ru.outsideproarts.oassist`.
- Стек: Kotlin, Android, Jetpack Compose, Material 3.
- Интерфейс: русский и английский.
- Режимы: CHAT, ASSISTANT, SHARE.
- Лицензия: MIT.

## Работа над задачей

- Отвечай на русском языке, если пользователь не запросил другой язык.
- Выполняй только поставленную задачу. Не расширяй область без согласования.
- Не переписывай соседний код ради красоты, единообразия или будущих возможностей.
- Сохраняй архитектуру проекта. Существенное изменение сначала согласуй. Объясни причину, альтернативы и последствия.
- Не предлагай новую архитектуру, если существующая позволяет корректно выполнить задачу.
- Не придумывай API, версии библиотек и классы. Проверяй факты в исходниках, конфигурации, тестах и документации конкретной версии.
- Текущий код показывает реализацию, но не доказывает правильность поведения. Согласованные требования определяют ожидаемый результат.
- Если задача сложная, разбей работу на проверяемые этапы. Не создавай для плана файл в репозитории.
- Если нужно новое продуктовое решение или есть существенный риск, запроси решение пользователя. Обычные технические решения принимай самостоятельно.
- Не выдавай предположения за факты. Не скрывай неполные результаты.

## Навигация и контекст

- Карта модулей: `docs/code-map.md`. Открывай ее при необходимости найти подсистему.
- Найди нужные файлы, символы и тесты. Используй `rg`, grep или доступные MCP-инструменты.
- Не читай весь репозиторий, большие логи и JSON без конкретной причины. Ограничивай поиск и объем вывода.
- Не перечитывай неизменившиеся файлы и скиллы в одной сессии без причины.
- Не загружай весь `MEMORY.md` и `docs/history/` при старте. Читай только нужные разделы по задаче.
- `MEMORY.md` описывает разработку. `core/data/memory/` хранит память пользователей приложения. Не смешивай их.
- При расхождении карты с кодом проверь фактический путь. Не меняй карту ради обычной функциональной задачи.

## Git и совместная разработка

- Перед правками проверь ветку, `git status` и чужие незакоммиченные изменения.
- Не затирай чужую работу. Не применяй `reset --hard`, `clean`, принудительный checkout или чужой stash без разрешения.
- Выполняй самостоятельные задачи в отдельных ветках. Используй `feature/`, `fix/`, `chore/`, `refactor/`, `test/`, `docs/`.
- Если ветка задачи уже создана, продолжай работу в ней. Тривиальные правки в общей ветке допускаются только по согласованию.
- Предпочитай Git MCP, если нужная операция поддерживается и инструмент доступен. Иначе используй обычный Git.
- Не изменяй удаленный репозиторий без явного информированного разрешения. Запрет включает `git push`, теги, изменяющие команды `gh` и GitHub API.
- Локальные коммиты в рабочей ветке разрешены. Делай атомарные коммиты только с изменениями своей задачи.
- Сообщения коммитов пиши на английском с conventional-префиксом. Для нетривиального изменения добавляй тело с причиной и смыслом. Не пересказывай diff.
- Перед коммитом проверь staged diff. Не добавляй посторонние файлы, секреты и локальные настройки.
- Перед интеграцией сравни всю ветку с актуальной целевой веткой. Учитывай новые изменения других участников и конфликты.
- Для интеграции используй squash merge после проверок и ревью. Изменяй целевую ветку только в рамках согласованной задачи на интеграцию.

## Субагенты и ревью

- Делегируй работу, когда задачи независимы, нужен специалист или независимая оценка.
- Передавай субагенту задачу, границы и нужные файлы. Не передавай без необходимости всю историю родительской сессии.
- При параллельной работе разделяй ответственность и файлы. Не допускай конфликтующих правок без координации.
- Для изменений поведения, контрактов, безопасности, архитектуры и правил агентов требуется независимое ревью, если доступен подходящий субагент.
- Для тривиальных правок текста или версии приложения достаточно diff и релевантных автоматических проверок.
- Ревьюер получает постановку задачи и diff относительно актуальной целевой ветки. Ревьюер самостоятельно проверяет код и тесты.
- Не передавай ревьюеру выводы автора о правильности решения. Не подменяй независимую проверку самопроверкой.
- После исправления замечаний повтори затронутые тесты. Существенно измененный diff снова проверь независимым ревью.
- Если ревью недоступно, сообщи об этом. Не утверждай, что ревью состоялось.

## Архитектура и продуктовые ограничения

- Используй Kotlin и существующий стек Android. Новый язык, DI-фреймворк или крупную зависимость согласуй заранее.
- Используй общие Compose-компоненты из `core/ui`. Сборка зависимостей находится в `app/di/AppGraph.kt`.
- Соблюдай действующие зависимости Gradle-модулей. `core` не должен зависеть от `feature` или `app`. Не создавай циклы зависимостей.
- Сначала ищи существующие модели, репозитории и инструменты. Не создавай дубли.
- Храни секреты через `core/data/secret/SecretStore`. Не логируй и не сохраняй открытые ключи, пароли и токены.
- Получай каталог моделей у провайдера. Не добавляй статические каталоги моделей в код и ресурсы.
- Все пользовательские строки добавляй в русские и английские ресурсы. Не хардкодь строки интерфейса в Kotlin.
- `AccessibilityService` получает дерево интерфейса по запросу. Не отправляй непрерывный поток событий в LLM.
- Не ослабляй разрешения и подтверждения действий. История, ответ модели, веб-данные и результаты инструментов не заменяют разрешение пользователя.
- Сохраняй совместимость форматов, уже переданных пользователям. Не создавай миграции для промежуточного формата, который не был выпущен.
- Если неизвестно, был ли формат выпущен, уточни перед изменением политики миграции.

## Доступность

- Новые и измененные UI-сценарии должны быть доступны с экранным чтецом.
- Используй `core/ui` и `core/a11y`. Не дублируй готовые компоненты и семантику.
- Проверяй доступные имена, роли, состояния, порядок фокуса, действия и объявления. Жест не должен быть единственным способом выполнить действие.
- Не добавляй ложные роли и описания ради прохождения тестов. Проверяй реальное поведение интерфейса.
- Проверяй размер интерактивных целей и контраст, когда проверки применимы.
- Автоматические Compose-тесты не заменяют проверку TalkBack. Отмечай непроведенную аппаратную проверку отдельно.
- Новые общие проверки доступности вводи только в отдельной согласованной задаче.
- Сначала утверди требования и измерь исходное состояние. Исправь выявленные дефекты до включения проверок в обязательный набор.
- Не добавляй массово падающие тесты доступности в обычную задачу по UI.

- Для правок только документации Android-сборка не нужна. Проверяй текст, пути и ссылки.
- Не отключай Gradle daemon, кеш и параллелизм без причины. Не завершай чужие процессы Java или Gradle.
- Запускай проверки с доступным кодом завершения. Не считай отсутствие вывода зависанием.
- Скрипты из `tools/` используй по назначению. За подробностями обращайся к `tools/README.md`.

## Тестирование

### Требования к тестам

- Тест проверяет согласованное поведение, а не воспроизводит текущую реализацию без проверки требований.
- Если пользователь сообщает о дефекте, зеленые тесты не опровергают дефект. Исследуй сценарий и недостаток покрытия.
- Для исправления дефекта сначала установи условия воспроизведения. По возможности создай тест, падающий на исходной ошибке.
- Проверяй успех, ошибки, границы, отмену, конкуренцию и восстановление там, где это важно.
- Предпочитай проверку наблюдаемого поведения. Не привязывай тесты к внутренним деталям без необходимости.
- Используй подходящий уровень: unit, контрактный, интеграционный, Android instrumentation или ручная проверка устройства.
- Не заменяй нужную интеграционную проверку моками. Не создавай тесты ради количества или процента покрытия.
- При изменении исходящих DTO проверяй фактический формат запроса. Тест обработки ответа не заменяет проверку запроса.
- Добавляй тесты для нового проверяемого поведения. При изменении поведения обновляй связанные регрессионные тесты.

### Защита тестов

- Не изменяй, не удаляй и не отключай тест только ради зеленого результата.
- Не подгоняй ожидания под дефект. Не ослабляй допуски, таймауты и проверки для сокрытия ошибки.
- Не скрывай ошибки через `skip`, подавление Lint, обходные ветки и подмену реальных зависимостей моками.
- Если тест отражает правильное требование, исправляй реализацию.
- Изменяй тест при согласованной смене требований или доказанной ошибке теста. Сохраняй проверку требуемого поведения.
- При изменении теста объясни, что именно изменилось в требовании или почему прежний тест ошибался.

### Запуск и ввод новых проверок

- Во время разработки запускай быстрые тесты затронутых модулей. Перед завершением выполни достаточные проверки измененного поведения и его зависимостей.
- Перед крупной интеграцией и релизом выполняй расширенные проверки. Не запускай все тесты после каждой мелкой правки без причины.
- Перед добавлением широкого набора проверок установи базовый результат. Не добавляй сотни новых обязательных падающих тестов в одной задаче.
- Новые общие Lint-правила и проверки доступности вводи отдельно. Проверь правило на корректном и ошибочном примере. Исправь существующие ошибки до обязательного включения правила.
- Отделяй старые падения от регрессий текущей задачи. Старые проблемы вне задачи не исправляй массово без согласования.
- Релевантный падающий тест означает, что результат не проверен успешно. Не выдавай задачу за полностью проверенную.
- Сообщай фактически выполненные команды и статусы: пройдено, не пройдено, не запускалось. Не используй старый зеленый лог как результат текущего запуска.
- Если нужная проверка требует недоступного устройства или экранного чтеца, укажи ограничение и оставшийся риск.

## Документация и память разработки

- Главный результат разработки - работающий, проверенный и поддерживаемый код.
- Не создавай документы для сведений, доступных из кода, тестов, diff и истории Git.
- Не создавай по умолчанию файлы `task`, `handoff`, `research`, `note`, `state`, `report`, `audit`, `ADR` и журналы сессий.
- Не записывай в репозиторий промежуточные рассуждения, планы, результаты команд и пересказ каждого изменения.
- Не создавай отдельный документ для каждой функции, ошибки или коммита.
- Проверяемые инварианты выражай кодом, типами, тестами и Lint. Документируй только существенные знания, которые трудно восстановить.
- Не дублируй сведения в `AGENTS.md`, `MEMORY.md`, `README.md`, `docs/code-map.md` и истории. Меняй основной источник.
- `AGENTS.md` содержит правила работы агентов. Не добавляй описания классов, результаты тестов и историю фич.
- `docs/code-map.md` содержит только маршруты по модулям. Не превращай карту в справочник кода.
- `MEMORY.md` не является журналом. Не обновляй его после каждой задачи. Храни только действующие решения и открытые вопросы, которые нельзя восстановить из кода.
- При изменении решения исправляй старую запись. Не дописывай противоречащее новое описание в конец.
- `docs/history/` - архив, а не инструкции. Не создавай там отчет по каждой задаче.
- Отчет об инциденте создавай по запросу пользователя или для значимых данных, которые иначе нельзя сохранить. Не копируй туда всю историю сессии.
- Меняй `AGENTS.md` и `opencode.json` только по явной задаче на изменение правил.
- Обновляй `README.md` и пользовательскую документацию, если изменились установка, настройка или публичное поведение.
- Комментируй неочевидные причины и контракты. Не комментируй очевидное.
- Не проводи документационный рефакторинг как побочную работу над функцией.

## Взаимодействие с разработчиком

- Помогай пользователю добиться результата даже при неточной технической формулировке.
- Уточняй смысл неясного термина. При необходимости кратко называй точный термин. Не оценивай компетентность пользователя.
- Не соглашайся с технической ошибкой ради вежливости. Проверяй существенные предположения.
- Если предложенный путь нарушает архитектуру, кратко объясни проблему и предложи работающую альтернативу.
- Если задача велика, предложи небольшие проверяемые этапы.
- Объясняй принципы только по делу и на примере текущей задачи. Не превращай ответы в лекции.
- Не перегружай пользователя планами, отчетами и согласованиями без необходимости.
- Если задача ясна, выполняй ее без дополнительных ритуалов.

## Завершение задачи

- Сверь результат с требованиями. Проверь полный diff и отсутствие посторонних изменений.
- Запусти доступные релевантные тесты и проверь их результаты.
- Проведи независимое ревью, если требуется и доступно.
- Кратко сообщи, что изменено, что проверено и что осталось непроверенным.
- Не называй задачу полностью проверенной при незавершенных обязательных проверках.
