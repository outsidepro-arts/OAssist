# MEMORY.md — актуальное состояние OAssist

Срез: 2026-10-27. Это память разработки репозитория; пользовательская память
установленного приложения хранится отдельно через `MemoryStore`.

Рабочие правила и UI-рецепты — в [AGENTS.md](AGENTS.md). Здесь перечислены текущее
состояние, действующие решения и открытые вопросы. Причины решений и прежние
результаты — в [указателе истории](docs/history/README.md): открывайте только нужную
тему, не весь архив. Срез составлен по коду и сохранённым записям; проверки прежних
изменений ниже не означают, что весь проект повторно протестирован при редактуре.

## Реализовано

- Android-клиент на Kotlin/Compose, ручной `AppGraph`, minSdk 31, compileSdk 36.
  Фактические модули — в `settings.gradle.kts`, версии — в Wrapper и version catalog;
  машинные пути SDK/JDK не являются требованиями проекта.
- Режимы CHAT, ASSISTANT и SHARE имеют отдельные провайдер, модель и initial prompt.
  VIS/session передаёт управление оверлею; AssistActivity — запасная точка входа.
  Профили, язык, доступы, речь, инструменты, память и навыки настраиваются в приложении.
- Протоколы: OpenAI Completions, OpenAI Responses, Anthropic Messages, Gemini;
  OpenCode Zen/Go — агрегатор, а не удалённый `opencode serve`. Список моделей
  запрашивается у провайдера; протокол агрегатора выбирается по override → models.dev
  → эвристике. Запись models.dev не заменяет список моделей провайдера.
- Встроенные инструменты и approval находятся в `core/agent`; MCP-клиент — в его
  `mcp/`. Внешние инструменты поступают от настроенных MCP-серверов по Streamable HTTP.
  Отдельных модулей `core/tools` и `core/mcp` в текущей сборке нет.
- Room хранит диалоги и ходы, медиа — отдельными файлами. Есть список/поиск диалогов,
  сохранение по настройкам режима, закреплённый диалог ассистента, Share в новый или
  существующий диалог. Авто-именование: плейсхолдер и название от модели строятся по
  первому текстовому сообщению; для аудио-первого сообщения MODEL_AUDIO seed — первый
  ответ ассистента (решение пользователя), без ответа имя остаётся пустым. Память
  пользователя и навыки общие для режимов.
- Названия новых диалогов запрашиваются отдельно через `ModelClient`, без агентского
  цикла, каталога инструментов, MCP и подтверждений. При ошибке или непригодном ответе
  остаётся локальное название; сохранённые и ручные названия не пересоздаются.
- Runtime-контекст разделяет инструкции владельца и данные памяти, экрана и SHARE.
  Общая политика доверия действует и для пользовательских/пустых промптов;
  удаление плейсхолдера памяти, навыков или экрана не подключает этот источник.
  Явно переданный SHARE-контент сопровождает просьбу. Новые SHARE-ходы
  сохраняют просьбу отдельно от контента; старые записи читаются без переписывания.
- Общие runtime-правила достоверности, обращения с секретами доступа и подтверждений
  действуют во всех трёх режимах, включая сохранённые пользовательские/пустые промпты.
  Новые дефолтные шаблоны не дублируют их; сохранённые тексты не переписываются.
- При подготовке контекста `HistoryBudget.trimHistoryAudio` оставляет только последний
  аудиоход истории, удаляя прежние audio-вложения с сохранением текста/placeholder.
  Ранний вопрос о раздувании контекста base64 этим закрыт; хранение медиа диалогов — отдельный слой.
- Системный STT поддерживает выбор RecognitionService отдельно для каждого режима;
  также есть RAW MODEL_AUDIO. Запись поддерживает Bluetooth-гарнитуры (AUTO-маршрут,
  см. «Речь и жизненный цикл»). Доступны системный TTS и экранный чтец. ONLINE_TTS
  оставлен в модели данных, но не реализован как рабочий канал; HTTP STT отложен.
- Голосовой инструмент voice_listen_start ожидает один распознанный ответ прямо
  в вызове. Stop управляет только ещё активным захватом своего агента и не возвращает
  прошлые ответы. Ошибки имеют неуспешный статус; отмена/таймаут очищают только свой
  захват, контроллер изолирован на агентский цикл при общем VoiceListener.
- Shizuku UserService/root обслуживают привилегированные операции. На MIUI/HyperOS
  BgStartGuard выявляет известную блокировку фонового запуска; исправление требует
  явного действия и доступных привилегий либо adb, универсальный обход не гарантируется.

## Действующие решения и ограничения

### Речь и жизненный цикл

- Ответ и нарратив — разные каналы. SCREEN_READER передаёт завершённые предложения
  через `ScreenReaderSpeaker` / `View.announceForAccessibility` (`TYPE_ANNOUNCEMENT`);
  видимый поток ответа не является live region. Старый рецепт скрытого LiveRegion
  для ответа отменён. Нарратив озвучивается только экранным чтецом и включается отдельно.
- Ручная остановка голосового ввода **системного ассистента** отменяет STT и отправляет
  последний partial. Для движков без partial вопрос может не отправиться. Пользователь
  отложил изменение на ожидание final; не менять эту семантику попутно с выбором сервиса
  или исправлением переподключений.
- **Чат:** обычный toggle сохраняет автоотправку final по тишине. Touch hold стартует
  после long-press threshold; ранний final буферизуется до принятого отпускания,
  отменённый/слишком короткий захват и dispose не отправляют текст. Semantic click,
  long-click/custom action и клавиатура переключают ввод без искусственного hold.
  Не смешивать это поведение с partial-on-stop ассистента.
- Запись голоса сопровождается звуками `voice_start`/`voice_finish` (чат PTT/toggle и
  оверлей ассистента, гейт `soundEnabled`): start — только при успешном старте захвата,
  finish — при любом конце, включая отмену и ошибку, один раз на сессию; `msg_send` для
  голосовых сообщений не гасится (двойник осознанно). Тул `voice_listen_*` звуков не
  получает. Guard'ы от двойного finish и раскладка хуков — в истории звуков.
- Выбранный RecognitionService хранится как полный компонент; null означает системный
  default. Если компонент исчез, применяется default без удаления пользовательского выбора.
  Названия сервисов не заменяют идентичность компонента; списки брендов не нужны.
- **Bluetooth-ввод (2026-10-27):** AUTO-маршрут записи per-mode (`SttConfig.bluetoothInput`,
  дефолт true): при подключённой BT-гарнитуре и выданном `BLUETOOTH_CONNECT` —
  `setCommunicationDevice` на сессию захвата (STT и RAW, через retry-политику), иначе
  микрофон. Контракт API: передаётся **sink** из `getAvailableCommunicationDevices()`
  (input-устройство отклоняется — это была причина молчаливого фолбэка на микрофон);
  RAW дополнительно закрепляет BT-вход через `AudioRecord.setPreferredDevice`.
  Запрос разрешения — один раз: чат/настройки — system launcher, оверлей —
  `ConsentActivity` + `PermissionRequestBridge` (фолбэк «Выдать» в уведомлении);
  отказ не блокирует запись. SCO-задержка не выжидается (начало записи может
  быть тихим), на время записи вывод уходит в гарнитуру в низком качестве. Потеря
  гарнитуры mid-capture — откат в микрофон с подсказкой. STT-движок работает
  в чужом процессе — его маршрутизацию мы не контролируем; следующий рычаг при
  проблемах — `MODE_IN_COMMUNICATION` на время захвата (сознательно не включён).
  Подробности и компромиссы — в истории Bluetooth-ввода.
- SpeechRecognizer переиспользуется после terminal final/error для того же сервиса
  и при допустимом retry, кроме ошибок, требующих пересоздания. При настоящей отмене,
  смене сервиса, `ERROR_SERVER_DISCONNECTED`, исключении старта, `ERROR_CLIENT`,
  `ERROR_TOO_MANY_REQUESTS` или close освобождается; старые callback изолированы от нового захвата.
  Disconnect допускает ограниченный retry только до первого partial. Callback закрытого
  экрана/сервиса не должен удерживаться кэшированным recognizer. Подробности — в истории STT.
- Compose-анимации drawer запускаются из composition scope с frame clock; длительные
  операции чата живут в ViewModel. `CoroutineExceptionHandler`, скрывающий исключение
  как молчаливый отказ, пользователь отклонил: ошибку нужно обработать и показать.

### Контракты инструментов и данных

- `ui_click`/`ui_long_click`: действие Accessibility-узла → прежний `input tap`/
  `input swipe` через Shizuku/root. Дополнительный координатный жест
  AccessibilityService отменён по решению пользователя после диагностики Jieshuo;
  без привилегий координатный резерв этих двух инструментов недоступен.
  Проверка `isLongClickable` и скрытие оверлея на время координатной попытки
  сохранены. У `ui_swipe` остаётся прежний dispatchGesture с привилегированным резервом.
- `shell_get_setting`/`shell_put_setting`: сначала прямой Android Settings API
  с правами приложения, при ошибке или `putString=false` — прежний исполнитель
  Shizuku/root. Отсутствующее/пустое значение не требует резерва; отмена задачи
  не запускает привилегированный повтор. Минимальные привилегии этих двух тулов
  теперь NONE; группы подтверждений PRIVILEGED READ/WRITE сохранены. `shell_exec`,
  восстановление сервиса, обход чёрного кадра и исправление MIUI не меняются.
- `alarm_set`/`timer_set`: `package` необязателен; конкретное приложение определяется
  через `app_list`/память или уточнение. Не зашивать перечень обработчиков в tool schema.
  Результаты alarm_set/timer_set и sms_send подтверждают только передачу запроса Android;
  создание/запуск, отправка и доставка SMS явно отмечаются как неподтверждённые.
- `ui_screenshot_region` при выходе координат за окно возвращает ошибку; автоматический
  clamp изменил бы согласованный контракт. Скриншоты учитывают временное скрытие оверлея.
- Скрытые Accessibility-действия включают действия с label, `long_click` и расширенные
  стандартные действия. Исключены базовые действия, уже отражённые отдельными инструментами,
  и внутренняя навигация TalkBack. Неизвестные расширенные id сохраняются; список получается
  по запросу `ui_get_actions`, а не раздувает каждый снимок. Индексы нод относятся к снимку.
- Настройки и JSON сохраняют совместимость старых данных. При изменении DTO проверяется
  исходящее тело запроса, включая обязательные значения по умолчанию: история уже содержит
  несколько регрессий этого класса. Конкретные тесты и причины — в указателе провайдеров/MCP.
- Секреты остаются в SecretStore, сохранённый plaintext не переотображается. Промпты
  приложения используют пользовательскую память, а не этот файл и не журнал разработки.
- История и результаты инструментов не удостоверяют разрешения. SYSTEM из истории
  понижается до данных; статусы текущих результатов привязаны к выполнению, а повторные
  tool id нормализуются только в транспортной копии. Только успешный текущий встроенный
  `skill_get` добавляет инструкции включённого навыка. Responses replay принимает
  проверенные reasoning items, а не произвольные элементы input.

- Подтверждения вызовов обслуживает существующий механизм приложения с учётом
  сохранённых разрешений: общее «после подтверждения» не требует второго вопроса
  в чате. Явное требование владельца отдельно спрашивать перед действием сохраняется.
  Разрешение инструмента не задаёт цель и не расширяет просьбу. Это выбранная
  совместимая трактовка, а не гарантия свежего согласия при каждом вызове.
- Отказ владельца нельзя обходить другим инструментом. Техническая ошибка сама
  по себе не является отказом; разрешённый запасной способ остаётся допустимым.
  Правило достоверности не требует дополнительной проверки после каждого инструмента.

## Открытые вопросы и отложенный объём

Это единый текущий список. Отложенное не является автоматически разрешённой задачей;
при реализации или новой проверке обновляйте пункт, а не копируйте его в конец файла.

| Вопрос | Статус / граница |
|---|---|
| Нажатия при Jieshuo browse by touch | На Mi 10/API 36 dispatchGesture не активировал строку поиска при browse by touch, пользовательский `adb input tap` активирует цель. Прямой ACTION_CLICK на строке вернул false. Дополнительный жестовый резерв ui_click/ui_long_click отменён пользователем; прежний Shizuku/root-резерв сохранён. Универсального решения без привилегий пока нет; работа с TalkBack не проверена. Подробности — [диагностика](docs/history/jieshuo-touch-exploration-2026-10-26.md) |
| Ручной выбор BT-гарнитуры, вывод звука в гарнитуру, LE Audio | Отложено; реализован AUTO-маршрут записи (см. «Речь и жизненный цикл» и историю Bluetooth-ввода) |
| Ручной stop ассистента для STT без partial | Ожидание final отложено пользователем; действующее поведение описано выше |
| SCREEN_READER и нарратив в notification-режиме (`showOverlay=false`) | Нет оконного якоря ScreenReaderSpeaker; полноценная озвучка в этом режиме не подтверждена, решение не определено |
| Голосовые инструменты после исправления протокола | На устройстве проверить завершение микрофона при отмене хода, соседство с PTT/RAW и TalkBack-подписи stop. TTS-вопрос не синхронизирован с открытием микрофона; per-mode RecognitionService в voice tools не передаётся — отдельные существующие ограничения. [Решение и проверки](docs/history/agent-voice-protocol-2026-10-27.md) |
| Инструменты per-mode | Сейчас общий каталог; отдельные наборы — возможное расширение |
| Сохранение чата при переключении | Независимый review выявил прежний отдельный риск: завершение асинхронного создания/сохранения может присвоить `chatId` уже после смены чата. Защита запоздавшего автоназвания этот путь не меняет; требуется отдельная проверка и исправление |
| Смысловая prompt injection | Структурное разделение runtime-контекста не гарантирует поведение любой модели. Внешние данные, медиа и документация MCP остаются видимыми; при сохранённом ALLOW ошибка модели может выполнить разрешённый инструмент. Реальные adversarial-сценарии ещё не проверены; [границы решения](docs/history/runtime-context-isolation-2026-10-26.md) |
| Шифрование Room-истории | Дополнительное шифрование истории отложено; это не отменяет SecretStore и redacting |
| Custom IME для стороннего UI | Отложено; текущий путь — доступные Accessibility/clipboard-действия |
| Онлайн-речь | ONLINE_TTS и кастомный HTTP STT отложены; не считать готовыми по наличию enum или старой roadmap |
| MCP-сервер самого OAssist | Был в исходном плане v1; текущая реализация содержит клиент. Реализация серверной поверхности — отдельный незавершённый объём, а не готовая возможность |
| Перехват кнопок через Xposed / Gemini / XiaoAI / Breeno | За пределами v1; штатный вход — системный assist-жест |
