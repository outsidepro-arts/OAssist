# Повторная проверка агентских контрактов, 2026-10-27

Проверена текущая ветка `fix/runtime-prompts`. Три исследовательских субагента
сверили все 11 пунктов исходного аудита с реализацией и тестами, без чтения архива.
Исходное дерево содержало только неотслеживаемый каталог `.serena/`; он не включён
в изменения задачи. Разработка выполнялась в Windows, через Serena текущей копии.

## Принятые решения

Для каждого исправляемого пункта привлечены две новые экспертные роли с независимым
анализом и перекрёстным обсуждением. Реализация передана worker; перед каждым
коммитом проведено отдельное независимое ревью, включая соответствующий абзац памяти.

- Пункт 4: сохранить совместимую трактовку существующего Approval Gate.
  Одно разрешение относится к вызову, сессионное — к группе в указанном режиме,
  сохранённое — к группе до изменения настройки. Полный запрет любых следующих
  инструментов после отказа не вводится: он затронул бы независимые задачи.
  Запрет обхода семантического отказа остаётся обязательной инструкцией модели.
- Пункт 6: `success=true` подтверждает успешный возврат API передачи запроса.
  Это не подтверждение создания будильника/таймера или отправки/доставки SMS.
  Неизвестный результат сам по себе не основание повторять запрос. SMS callbacks
  и новая модель результата не требуются для устранения неточного сообщения.
- Пункт 7: полный каталог имён и заголовков вместо фрагментов процедур.
  Отсутствующий `{skills}` сохраняет прежнюю семантику. Полный навык допускается
  в инструкции только после успешного настоящего встроенного `skill_get` текущего хода.
  Ошибка, отказ, выключенный навык или одноимённый поддельный тул этого не делают.
- Пункт 8: правило включено в runtime-политику, описание `bye` и оба шаблона.
  Старые сохранённые промпты не переписываются. Явная отмена допускает завершение;
  «Спасибо, а теперь поставь таймер» сохраняет новую задачу. Классификатор текста
  в исполнителе не добавляется.

- Пункт 9: каждый явно индексный инструмент требует UUID `snapshot_id` из последнего
  `ui_get_screen`. Старый токен после нового снимка или перезапуска не может совпасть
  с новым. Сохранённая копия Android-узла сравнивается со свежим по идентичности,
  окну, пакету и наблюдаемым свойствам; одного совпадения текста недостаточно.
  Скрытые действия привязаны к ранее выданной последовательности id/label.
  Mutex защищает владение снимком; временные и сохранённые ссылки освобождаются.
  Резерв Shizuku/root повторно сверяет исходную цель после скрытия оверлея.
  Изменяющие попытки инвалидируют снимок после завершения, включая резерв.
  Дополнительный координатный Accessibility-жест не возвращён.
- Пункт 10: используется признак усечения фактически выбранного источника плюс
  ограничение итогового текста. Полный Markdown-заменитель не наследует усечение
  отброшенного HTML; собственное усечение Markdown и DOM сохраняется. HTTP проверяет
  один байт за лимитом, DOM — один символ. Отсутствие известного усечения не означает
  полноты страницы. Уведомления считаются после фильтрации собственных, до лимита 20;
  ошибка чтения не маскируется пустым списком.

Экспертные пары: `approval_expert_a/b`, `outcome_expert_a/b`, `skills_expert_a/b`,
`bye_expert_a/b`, `ui_expert_a/b`, `partial_expert_a/b`. Реализация: отдельные worker
для каждого пункта. Ревью: отдельные reviewer для каждого коммита; UI дополнительно
проверен независимым reviewer по конкурентному доступу и жизненному циклу ссылок.
Подтверждённых оставшихся замечаний ревью нет.

## Проверки и границы

До правок прошли 386 JVM-тестов `core:agent`; после пунктов 4, 6, 7 и 8 —
повторный успешный запуск на стабильном снимке кода. Использован установленный JDK 21
и штатные общие кэши; Wrapper 9.4.1, без отключения демонов и ограничений workers.
Один промежуточный запуск во время правки теста навыка выявил неверное сравнение
исходного текста с JSON-экранированным tool result; worker исправил проверку,
а полный исходный текст по-прежнему проверяется в SYSTEM следующего запроса.

Тесты промптов проверяют доставку правил, а не семантическое послушание реальных
моделей. Структурное разделение данных не даёт абсолютной защиты от prompt injection.
Сохранённое ALLOW не означает свежего подтверждения каждой операции.

ADB доступен, подключённых устройств при проверке нет. Реальный Android-узел,
микрофон, взаимодействие с приложениями часов/SMS и TalkBack не проверялись.
Итоговый стабильный снимок после всех шести исправлений:

- `:core:agent:testDebugUnitTest`: 396 тестов, 0 failures/errors/skipped.
- `:app:assembleDebug`, `:app:lintDebug`, `:core:agent:lintDebug`: успешно.
- Первый общий запуск остановился на AccessDeniedException при записи
  `core/agent/build/intermediates/aar_main_jar/debug/syncDebugLibJars/classes.jar`.
  Повтор той же команды вне песочницы завершился успешно за 1 мин 24 с.
  Исходники между проверкой и коммитами не изменялись.
- Тесты UI проверяют реестр, свойства, смену токенов, скрытые действия и обязательность
  параметров. Они не проверяют настоящее Android-равенство узлов или фактический
  привилегированный ввод. Изменение внешнего UI между последней сверкой и действием
  остаётся возможным.
- MockEngine проверяет HTTP, HTML/article/fallback и Markdown-пути; DOM проверен
  чистой граничной функцией, не исполнением JavaScript внутри WebView.
- Реальные модели: новая задача после благодарности, соблюдение условий длинного
  навыка, отказ против технической ошибки и prompt injection остаются ручными сценариями.

`9db2115` (10), `9482951` (9). Ветка сохраняется без слияния в master.
