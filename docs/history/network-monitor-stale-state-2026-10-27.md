# Ложное отсутствие сети, 2026-10-27

Исходная ветка `fix/runtime-prompts`, коммит `2df33f4`. Пользователь сообщил,
что установленный актуальный APK показывает «нет сети» в чате и ассистенте,
хотя интернет работает. Диагностика выполнена на подключённом Mi 10, Android API 36.
Сетевые настройки и данные приложения не менялись.

## Подтверждённые факты

- SHA-256 установленного APK совпал с предыдущей локальной сборкой, до изменения
  монитора сети. Код NetworkMonitor в коммите терминального прощания не менялся.
- В logcat сохранены доступные записи процесса; сетевых исключений не найдено.
  Старый монитор подавлял ошибки опроса и регистрации через runCatching без лога.
- INTERNET и ACCESS_NETWORK_STATE выданы. Default Wi-Fi имеет INTERNET и VALIDATED;
  эффективной блокировки UID в netpolicy нет. HTTPS HEAD к example.com, выполненный
  через run-as от UID OAssist, получил HTTP 200 с обычной TLS-проверкой.
- Чтение полей уже запущенного APK через JDWP подтвердило started=true и
  NetworkMonitor._isOnline=false; sequence StateFlow оставался 0. Системный dump
  подтверждает зарегистрированный обычный LISTEN callback, без blocked handler.
  После чтения потоки возобновлены, отладчик отключён, временный порт удалён.
- Подтверждено устаревшее отрицательное состояние наблюдателя. Точная исходная
  последовательность событий, приведшая к нему, не установлена; её не следует
  представлять как доказанную конкретную гонку или ошибку прошивки.

Внутри песочницы ADB не видел USB. Для телефона использован системный ADB вне
песочницы. Короткий первый logcat-фильтр оказался слишком узким; затем сохранён
доступный ограниченный журнал процесса без этого фильтра, вне Git.

## Исправление

Старый callback повторно читал activeNetwork/getNetworkCapabilities вместо
переданных данных. Android предупреждает о stale/null гонках такого опроса
[в документации NetworkCallback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback#onAvailable(android.net.Network)).

- Используется registerDefaultNetworkCallback для сети самого приложения.
- Capabilities и блокировка берутся из аргументов callbacks. Для новой сети
  публикация ждёт обоих начальных payload; промежуточное true не запускает
  отложенный запрос на ещё заблокированной сети.
- Проверяются identity текущей сети и актуальность экземпляра callback; поздние
  события после stop/restart не меняют состояние. Ошибки регистрации оставляют
  start повторяемым; неудачная очистка callback повторяется перед заменой.
- Начальный snapshot выполняется до регистрации. Отсутствие activeNetwork означает
  offline; отсутствие capabilities или исключение — неизвестность, допускающую
  попытку. VALIDATED не добавлен как обязательное условие.
- Общий NetworkHandle и предварительные проверки UI сохранены. В logcat появляются
  изменения boolean-состояния и классы ошибок без SSID, URL, IP и секретов.

Два свежих эксперта согласовали решение; реализация выполнена worker и прошла
отдельное независимое ревью без подтверждённых оставшихся замечаний.

## Проверки и оставшиеся действия

На окончательном снимке с JDK 21 через Wrapper успешно выполнены:

- core/net testDebugUnitTest: 16 тестов, 0 failures/errors/skipped;
- core/net lintDebug;
- app assembleDebug, assembleDebugAndroidTest и lintDebug.

Десять новых JVM-тестов проверяют исправление отрицательного bootstrap по callback
payload, blocked/unblocked, handover без ложного online, поздние события,
неизвестный snapshot, ошибки регистрации и restart/cleanup. Проверка кода не
подменяет воспроизведение конкретной последовательности на телефоне.

Добавлен NetworkMonitorInstrumentedTest, opt-in через `-e verifyInternet true`.
Он выполняется в UID целевого приложения, проверяет отдельный монитор и общий
NetworkHandle, делает HTTPS HEAD с обычной TLS-проверкой и повторяет проверку
обоих мониторов. Ключи/провайдеры/история не читаются, сеть и настройки не меняются.

## Проверка пользовательской сборки на телефоне

Пользователь собрал основной и тестовый APK самостоятельно. Приватные ключи не
предоставлялись и не запрашивались. Агент сначала ошибочно отнёс к пользовательской
части также установку; это уточнение исправлено в текущей памяти. Перед обновлением
сравнены публичные сертификаты установленного и обоих подготовленных APK — они
совпали. Готовые APK установлены через ADB с `-r`, без удаления данных.

После обновления SHA-256 основного APK совпал с файлом пользовательской сборки;
UID и inode каталога данных сохранились. После проверки временный тестовый пакет
удалён, основной OAssist открыт обычным запуском. Копия прежнего APK для проверки
публичного сертификата удалена. Настройки сети не менялись.

Первый opt-in запуск на Mi 10/API 36 выполнил проверки UID, capabilities,
отдельного монитора и общего NetworkHandle. Затем HTTPS HEAD получил **403**.
Запуск завершился **неуспешно**: прежний assert разрешал только 200..399.
Проверки состояния мониторов после ответа не выполнялись — их нельзя считать
прошедшими. Получение 403 подтверждает HTTPS-обмен, но не разрешение доступа к
ресурсу и не успешность прикладной операции.

С двумя новыми экспертами согласована поправка только теста, реализована worker и
проверена независимым reviewer:

- Допускается любой окончательный HTTP-код 200..599; -1 и 1xx не принимаются.
- Redirect отключён для этого соединения: первый ответ уже достаточен для проверки.
- Проверка сертификата/имени узла, таймауты и транспортные исключения не изменены.
- Обе post-response проверки мониторов сохранены. В результат instrumentation
  выводится только числовой HTTP-код, без тела и заголовков. Промежуточный sendStatus
  не является итоговым результатом JUnit. После замечания ревью для него используется
  код IN_PROGRESS=2; код завершения 0 не используется для промежуточной диагностики.

`app:compileDebugAndroidTestKotlin` прошёл. Подготовленные пользователем APK не
перепаковывались и не переподписывались; SHA-256 основного файла не изменился.
Исправленный smoke-тест ещё не выполнялся на телефоне: потребуется собрать только
тестовый APK под пользовательским сертификатом. Это не требует пересборки основного
приложения, производственный код в этой поправке не менялся.

Пользователь отдельно подтвердил: обычные запросы теперь проходят, сообщение
«нет сети» исчезло. Исправление пользовательского сценария подтверждено этим
ручным проходом; оставшаяся проверка — повтор полного скорректированного smoke-теста.
