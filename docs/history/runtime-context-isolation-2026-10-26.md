# Разделение runtime-инструкций и данных — 2026-10-26

## Причина и независимый анализ

Экран, память и SHARE подставлялись в системный промпт обычной заменой строк.
Внешний материал не имел явно ограниченного статуса. Результаты инструментов и
внешняя документация MCP также не имели общего правила происхождения данных.

Два новых эксперта независимо исследовали безопасность и совместимость, затем
провели перекрёстный анализ предложений. Оба дополнительно выявили возможность
вставить произвольные элементы Responses input через сохранённый `replayJson`.

Согласованный приоритет: безопасность, затем расход провайдера, затем скорость.
Дополнительная модель для фильтрации контекста не используется.

## Реализация

- `RuntimePrompt` разделяет инструкции владельца и типизированные данные.
  Рендерер обрабатывает только плейсхолдеры исходного шаблона одним проходом.
  Память, экран и SHARE не подставляются сырым текстом в SYSTEM; включённые
  пользовательские навыки сохраняют назначение инструкций.
- Отсутствие плейсхолдера не подключает соответствующие память, навыки или экран.
  Пустые значения не создают блок данных. Исходный пользовательский шаблон не
  переписывается. SHARE как явно переданный материал сопровождает просьбу.
- На границе запроса агент добавляет общее правило доверия для всех режимов,
  включая пустые и пользовательские промпты. Текущая просьба и контекст передаются
  в сериализованной структуре. Вложенные строки с названиями ролей и плейсхолдерами
  остаются данными. Медиа сохраняют отдельные протокольные поля.
- Исторические SYSTEM не становятся инструкциями; некорректные группы вызовов
  деградируют в исторические данные. Корректные пары вызов/результат сохраняются.
  Транспортные обёртки строятся на копии и не записываются в историю.
- Только успешный текущий вызов настоящего встроенного `SkillGetTool` добавляет
  инструкцию владельца в текущий запуск. Отказ, ошибка, внешний одноимённый
  инструмент и старые результаты не повышают доверие. Разрешения gate не меняются.
- MCP-документация обозначена как внешняя справка по конкретному инструменту;
  JSON Schema сохраняется, включая вложенные описания и параметры с именем
  `description`. Общее правило ограничивает полномочия всей внешней схемы.
- Изображения результатов инструментов, которые протокол выносит в USER,
  получают явную подпись источника. Аудиоввод текущего владельца остаётся запросом.
- Responses replay допускает только проверенные reasoning-объекты и известные
  поля. Поддельные сообщения, роли и вызовы функций из replay не пересылаются.

Допустимая структура reasoning сверена с
[официальной спецификацией OpenAI](https://developers.openai.com/api/reference/resources/responses/methods/create)
и [руководством по reasoning](https://developers.openai.com/api/docs/guides/reasoning).
Изменение не переключает модели и не меняет настройки reasoning пользователя.

## Совместимость и границы

Новые SHARE-ходы сохраняют просьбу и внешний материал раздельно в дополнительном
JSON-поле; UI-текст, поиск и названия чатов используют прежнюю проекцию.
Старые payload читаются без этого поля. Они не разбираются по словам «Текст» или
«Вопрос»: достоверно восстановить происхождение уже смешанного текста нельзя.
Импортированные метки не удостоверяют владельческие инструкции или разрешения.
Room-схема и сохранённые промпты, память, навыки и approval-пресеты не сбрасываются.

Перекрёстный review обнаружил штатное повторение tool call id у Gemini и ошибочное
смешение статусов по одному id. Статус должен относиться к конкретному выполнению,
а преобразование идентификаторов на транспортной копии сохранять связанные пары.
Отдельно проверяется SHARE с завершающими переводами строк, чтобы не удваивать
переданный материал и не терять его пробелы при устранении дублирования.

Изоляция предотвращает структурное повышение роли данных, но не доказывает,
что любая модель отвергнет любую смысловую prompt injection. Внешние описания,
enum/default в MCP-схемах и содержимое медиа остаются видимыми модели. Извлечение
всей документации из JSON Schema не включено: оно меняет контракт инструментов
и не создаёт абсолютной гарантии. Ошибка модели при сохранённом ALLOW всё ещё
может привести к выполнению разрешённого инструмента; gate остаётся независимым
ограничением, его политика в этой работе не меняется.

## Проверки

Итоговая команда Wrapper завершилась успешно:

```powershell
.\gradlew.bat :core:agent:testDebugUnitTest :core:data:testDebugUnitTest :core:provider:testDebugUnitTest :core:model:testDebugUnitTest :app:assembleDebug :app:lintDebug --console=plain
```

- 626 JVM-тестов: `core:agent` 370, `core:data` 52, `core:provider` 162,
  `core:model` 42. Ошибок, падений и пропусков нет.
- Проверены фактически сериализованные HTTP-тела OpenAI Completions, Responses,
  Anthropic и Gemini через локальный SSE-сервер и обычный OkHttp-транспорт.
  Внешние API не вызывались. MockEngine не поддерживает требуемый SSECapability,
  поэтому новые потоковые wire-тесты используют loopback, ограничены таймаутами
  и закрывают сервер и клиент в `finally`.
- Проверены поддельные роли/разделители/плейсхолдеры, отключённые источники,
  точность SHARE с завершающими переводами строк, legacy и новый JSON round-trip,
  корректные и неполные tool-пары, коллизии history/live и два последовательных
  live-вызова с одинаковым id и разными статусами, ASK/отказ/выключенный навык/
  внешний двойник `skill_get`, ошибочный и допустимый reasoning replay.
- Бюджет изображений применяется до JSON-обёрток: служебные отметки остаются
  внутри полей данных, повтор запроса использует неизменённую проекцию раунда.
- Debug APK собран, `:app:lintDebug` завершился успешно; `git diff --check` чистый.
- Два новых эксперта провели независимый анализ, перекрёстную проверку и review
  реализации. Отдельный reviewer проверил весь diff и закрытие замечаний.
  После исправлений подтверждённых дефектов не обнаружено.

При проверках возникали ошибки очистки старых бинарных отчётов Gradle; повторные
запуски выполнялись без ручного удаления кэшей. Отдельная блокировка
`core/model/build/intermediates/compile_library_classes_jar/debug/bundleLibCompileToJarDebug/classes.jar`
исследована read-only через Windows Restart Manager. Владельцем оказался Gradle
daemon, а не предполагаемый language server. После `gradlew --status` подтверждено
отсутствие активных сборок и единственный IDLE daemon текущей версии; штатный
`gradlew --stop` освободил файл. Общие кэши не очищались, настройки окружения и
права файлов не менялись.

Проверки с реальными API, на телефоне и с TalkBack не проводились. Зелёные
детерминированные тесты подтверждают формирование запроса, сериализацию и
совместимость данных, но не заменяют проверку поведения реальных моделей.
